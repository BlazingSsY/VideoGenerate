# 智能体任务编排与画布接管改造计划

日期：2026-09-13。状态：已制定，待实施。

依据：当前工作区代码（含未提交改动）与本次功能审查。本文件安排后续改造；不代表下列功能已经完成。现有 `agent-v3-design.md` 保留为历史设计参考，实际能力以代码和验证结果为准。

目标是在现有视频模型能力范围内，让用户用自然语言完成画布搭建、参数修改、任务执行、进度查看、失败处理和局部重做。用户可以随时编辑画布或停止智能体继续操作。

## 1. 按难度与依赖排序

难度按涉及的数据一致性、执行状态和模型判断复杂度划分。人日为一名熟悉项目的工程师完成开发、回归和联调的粗估，不是交付时间承诺；各阶段验收后更新后续估算。

| 顺序 | 阶段 | 难度 | 预计人日 | 交付效果 | 前置阶段 |
| --- | --- | --- | --- | --- | --- |
| 1 | 修复现有执行入口 | 低 | 1–2 | 计划可接受，Auto 可启动，会话绑定正确画布 | 无 |
| 2 | 完整转换计划到画布 | 中低 | 2–3 | 节点、素材、连线和参数完整落图，界面及时更新 | 1 |
| 3 | 打通任务与画布的状态同步 | 中 | 3–4 | 执行有持续进度，结果回填节点，刷新后可恢复 | 2 |
| 4 | 开放画布操作工具与人工接手 | 中高 | 4–6 | 智能体能读取、修改现有画布，修改可以撤销 | 2、3 |
| 5 | 补齐调度、取消与失败重试 | 高 | 4–7 | 多步骤执行可控，依赖正确，失败可恢复 | 3、4 |
| 6 | 实现局部重新生成 | 高 | 3–5 | 只重做改动镜头及受影响的下游，复用其余结果 | 4、5 |
| 7 | 结果检查与有限自动修正 | 最高 | 4–7 | 根据结果发现问题，在预算和次数限制内调整重做 | 5、6 |

主线依次推进 1 → 2 → 3 → 4 → 5 → 6 → 7。第 6 阶段的单项工作量可能小于第 5 阶段，但依赖其运行版本和重试机制，不宜提前单独实现。

交付里程碑：

- **M1：可用的生成闭环**，完成 1–3，约 6–9 人日。自然语言出计划，画布完整落图，生成结果可追踪。
- **M2：可控的画布接管**，完成 1–5，累计约 14–22 人日。支持读写画布、撤销、人工接手、取消和重试。
- **M3：局部重做与结果修正**，完成 1–7，累计约 21–34 人日。形成现有视频能力范围内的完整任务闭环。

## 2. 已确认的起点

已有模块可复用：FastAPI 路由、React Flow 画布、模型目录、计划校验、图校验、视频生成与轮询、FFmpeg 合成、AgentRun/AgentTask、素材库、画布保存版本检查。

审查与隔离验证发现：

- `AgentDrawer` 发起轮次时未传当前画布 ID；转换计划接口因此找不到目标画布。
- Auto 二次校验传入空用户对象，合法生成计划也会在启动前报错。
- 规则降级计划写入了聊天消息，却未写入 `AgentTurn.plan`，接受计划返回 400。
- 计划转画布遗漏参考素材，重复导入的节点 ID 与连线引用也缺少统一映射。
- 规划结束发送 `done` 并清理队列；执行进度与规划事件共用生命周期，长任务无法持续展示。
- 工具注册表只有查询工具，执行记录没有完整绑定画布节点。

上一轮相关后端测试 75 项通过，前端类型检查通过；这些测试尚不能证明上述端到端链路成立。本次验证使用模拟模型响应和隔离数据库，未调用付费生成服务。

## 3. 第 1 阶段：修复现有执行入口

目标：先消除明确的阻断错误，保持现有交互结构。

改造任务：

1. 将当前画布 ID 从画布状态传到智能体抽屉；按画布恢复或建立会话，切换画布后不复用其他画布的绑定。没有目标画布时给出明确状态。
2. 后端校验会话、画布与当前用户的归属及绑定一致性；执行器不再把画布会话的目标改写成聊天对话 ID。
3. 合并 Ask 接受计划与 Auto 启动的公共服务，统一使用真实用户进行权限、计划有效性、过期、金额、节点数及每日预算检查。
4. 在一个事务内完成计划接受、预算预占和运行记录创建；重复接受返回既有结果或明确冲突，防止重复提交。执行失败和未提交任务的预算处理需有明确状态。
5. 规则降级与模型规划都写入 `AgentTurn.plan`；校验成功后的计划、估算和聊天计划快照保持一致。修复失败的计划不能进入执行。
6. 前端展示接受失败、转换失败和预算阻断原因，并按 `turn_id` 更新对应历史计划卡片的状态。

主要文件：`frontend/src/App.tsx`、`frontend/src/pages/Canvas.tsx`、`frontend/src/components/agent/AgentDrawer.tsx`、`AgentTranscript.tsx`、`PlanCard.tsx`，以及 `backend/app/routers/agent.py`、`agent_chat.py`、`agent_service.py`、`agent_executor.py`。共享服务提取到新模块，避免路由与编排器各维护一份执行规则。

验收标准：

- [ ] 有 Provider 的 Ask/Auto，以及无 Provider 的规则降级，都能产生可接受的合法计划。
- [ ] Auto 不再出现空用户错误，超自动额度时转 Ask，超过每日额度时拒绝启动。
- [ ] 同一计划重复点击或同时接受，只创建一次运行；已有成功计划不会被当作新计划重复执行。
- [ ] 在画布 A 发起的会话不会写入画布 B，跨用户目标被拒绝。
- [ ] 前端错误可见，执行按钮状态与对应计划一致。

## 4. 第 2 阶段：完整转换计划到画布

目标：把计划完整、可重复地转换成可执行画布，为后续工具写入建立共同入口。

改造任务：

1. 从现有图保存逻辑提取公共画布服务，统一处理归属、版本冲突、图与参数校验、事务写入。现有手动保存与计划导入均调用它。
2. 建立稳定的计划节点到画布节点映射，生成全局唯一节点和连线 ID；所有引用通过映射转换。以计划版本和目标画布作为导入幂等依据。
3. 转换提示词、生成节点、参考图片、首尾帧、参考视频/音频、输出节点及合法连线。参考内容按资产 ID 或受校验的媒体引用保存，不持久化即将过期的签名链接。
4. 保留模型、能力、时长、比例、分辨率、水印、音频和输出片段顺序；单镜头也提供明确输出。未支持的操作显式返回说明。
5. 分开表达执行先后依赖和实际素材连接：纯顺序依赖不伪造成媒体连线；数据连接只使用模型支持的输入槽位。
6. 导入前同步当前未保存编辑；导入成功后按返回的图与版本刷新界面，定位新增内容。版本冲突时保留本地编辑并提示处理，不静默覆盖。

主要文件：`backend/app/routers/agent.py`、`routers/canvas.py`、`canvas_graph.py`、`schemas.py`、`models.py`，以及 `frontend/src/pages/Canvas.tsx`、`components/agent/PlanCard.tsx`、`api.ts`。建议新增 `canvas_service.py` 与计划转换模块。

验收标准：

- [ ] 文生、图生、首尾帧、多参考素材计划转换后均能通过实际生成参数校验。
- [ ] 多镜头连接正确，输出片段顺序与计划一致。
- [ ] 同一计划重复导入不增加副本；不同画布导入同名镜头不发生主键冲突。
- [ ] 图校验失败时整次写入回滚，不留下半张画布。
- [ ] 导入后无需刷新页面即可看到内容，本地编辑不丢失。

## 5. 第 3 阶段：打通任务与画布的状态同步

目标：用户能看到从排队到成片的全过程，规划结束不影响生成任务继续跟踪。

改造任务：

1. 为 Run/Task 增加明确的画布、计划版本、画布节点和执行输入快照关联。使用第 2 阶段的映射，避免依靠节点名称猜测。
2. 画布场景的执行入口先确保计划已落图，再基于冻结的输入启动任务；已经手动修改过的图应重新校验或重新规划，不能悄悄运行旧计划。
3. 拆分轮次与运行生命周期：保留规划事件流，增加运行查询与运行事件流。接受计划及 Auto 启动均向前端返回 `run_id`；规划 `done` 只结束规划订阅。
4. 持久化关键运行事件，为每条事件分配独立游标；多个订阅者分别读取。状态变更与对应事件一致提交，不能依赖内存队列成为唯一记录。
5. 前端支持运行快照加载、断线续传、重复事件去重和页面刷新恢复，并按 run/task 身份更新历史消息及画布节点。
6. 任务完成时回填节点关联与输出资产；只更新匹配本次输入版本的结果，旧任务晚到不能覆盖新任务结果。
7. 保留已有后台恢复入口，统一恢复责任，避免普通生成恢复和 Agent 恢复同时调度同一个 Message。媒体链接在读取状态时重新签发。

主要文件：`backend/app/models.py`、`main.py`、`agent_executor.py`、`tasks.py`、`routers/agent.py`、`routers/canvas.py`、`media_links.py`，以及前端 API、任务列表、聊天记录和画布状态管理。

验收标准：

- [ ] 视频任务耗时超过规划结束后的队列清理时间，界面仍显示排队、运行、成功或失败。
- [ ] Ask 与 Auto 都能订阅运行，聊天卡片和画布节点指向相同结果。
- [ ] 刷新、断网重连或双标签页不会漏掉最终状态，不重复显示同一事件。
- [ ] 服务重启后续跟已有上游任务，不重复提交已经有供应商任务 ID 的生成任务。
- [ ] 旧任务完成时不会覆盖用户修改后的节点或新版本输出。

## 6. 第 4 阶段：开放画布操作工具与人工接手

目标：用户可以直接要求智能体操作现有画布，并能撤销和接手。

改造任务：

1. 提供 `canvas.read`、`canvas.inspect_node` 等读取工具；输入包含当前画布、用户选中节点、节点顺序、素材引用及运行状态。大量节点按需读取，后端重新确认归属与版本。
2. 增加受 schema 约束的 `canvas.apply_patch`，支持节点创建、更新、删除、移动、连接和断开；运行操作通过独立入口使用第 1、3 阶段的执行服务。
3. 修改类意图依据当前画布事实生成操作，不仅依靠上一版文本计划；“第二个镜头”优先按输出片段顺序解析，多个输出导致歧义时再询问。
4. 将通用工具注册表适配为各 Provider 接受的 function calling 格式，并验证工具名称与参数；不支持工具调用的模型退化为展示可执行计划，不能宣称已修改画布。
5. 每批操作必须携带基础图版本和幂等键，服务端校验整批操作后原子提交，返回新版本及变更摘要。第 2 阶段的公共服务成为所有写入入口。
6. 保存每批操作的逆操作或变更前快照，提供一次撤销；撤销也需要版本检查，不能恢复旧快照覆盖后续人工编辑。撤销图编辑不撤销已经发生的外部生成费用。
7. 提供“停止智能体操作／人工接手”控制，递增控制版本，使已在途的旧写操作失效；清理前端过期的自动保存请求。已经启动的视频任务保持可查看，其运行取消能力在第 5 阶段完善。
8. 沿用 Ask/Auto 的付费执行规则：明确要求的可逆图编辑直接执行并可撤销；视频生成与重新生成仍统一经过执行额度检查。

主要文件：`backend/app/agent_tools.py`、`agent_chat.py`、公共画布服务、画布操作记录和路由，以及 `frontend/src/pages/Canvas.tsx`、智能体抽屉、画布版本与撤销状态管理。

验收标准：

- [ ] “查看当前分镜”“把第二镜头改成近景”“新增一个结尾镜头并接到输出”能准确读取和修改现有节点。
- [ ] 提示词或外部素材中的内容不能绕过工具参数、归属、模型与图校验。
- [ ] 一次多节点修改可以整体撤销；撤销遇到后续编辑时给出冲突说明。
- [ ] 人工接手后，在途的旧智能体操作无法再覆盖画布。
- [ ] 手动操作与智能体操作应用同样的图规则，错误原因一致。

## 7. 第 5 阶段：补齐调度、取消与失败重试

目标：任务具有完整运行控制，失败后能够有界恢复。

改造任务：

1. 统一单节点运行、Agent 多节点运行和合成的任务控制入口，复用现有生成与合成实现。为不同运行保存不可变输入，避免把实时画布直接当成执行状态。
2. 调度就绪节点，校验输出节点存在，合成输入与依赖一致；上游成功且产物可用后才释放下游。独立节点可在用户、模型和全局并发上限内并行，默认从低并发开始。
3. 持久化任务领取、尝试次数、下一次重试时间和取消请求；进程恢复时依据数据库与上游任务状态恢复。
4. 区分轮询暂时失败、参数错误、供应商终态失败和提交结果未知。暂时错误有限退避重试；参数错误等待修正；新一次生成作为新尝试保存，不覆盖旧记录。
5. 处理上游已接受提交、但本地尚未保存 task ID 的崩溃窗口：优先用供应商幂等键或查询能力；不具备这些能力时标记结果待核实，不能盲目重提并声称绝不重复扣费。
6. 增加 Run/Task 的取消与重试接口。取消停止后续调度；已提交到外部的任务是否能真正终止取决于供应商能力，界面区分“停止后续任务”和“上游已取消”。
7. FFmpeg 合成可被终止，清理本次临时文件；上下游失败、取消后，未执行节点进入明确的阻塞或取消状态。
8. 每次重试重新检查预算与授权范围，持久化预占及释放记录；未知实际费用不能当作已退款。

主要文件：`backend/app/agent_executor.py`、`tasks.py`、`canvas_executor.py`、`models.py`、`main.py`、相关路由、任务控制组件。优先沿用当前单服务部署，出现明确容量需求后再评估外部队列。

验收标准：

- [ ] 两个独立镜头按并发上限运行，合成等待所需镜头成功；有依赖的节点绝不抢跑。
- [ ] 重复运行、重复重试和恢复调度不会创建相同的本地执行尝试。
- [ ] 上游超时、提交结果未知和确定失败分别进入正确处理路径。
- [ ] 取消后不再启动下游，重连后仍可看到取消状态和已提交任务的真实状态。
- [ ] 服务在排队、提交、轮询、合成阶段重启后均能恢复或明确报告待处理状态。

## 8. 第 6 阶段：实现局部重新生成

目标：修改某个镜头后，仅重做受影响部分。

改造任务：

1. 分开记录节点结构、执行输入版本和输出版本。输入指纹包含提示词、模型与参数、素材内容版本、上游产物版本及合成顺序/转场。
2. 区分数据依赖和执行顺序依赖；沿数据依赖计算需重做的下游。位置移动、缩放和纯执行顺序调整不使已有视频失效。
3. 创建派生运行，复用仍可访问且输入一致的成功产物；保留来源任务与版本，避免复制状态后丢失来源。
4. 只修改一个镜头时重新生成该镜头并重新合成；仅调整片段顺序或转场时，只重做合成。
5. 用户确认执行的对象绑定具体版本；旧任务完成、新指令到达、撤销编辑发生时，结果按版本隔离。
6. 旧产物被清理或参考素材已变化时，明确显示需要额外重做的节点及增加的费用。

主要文件：公共画布服务、计划到运行的编译逻辑、调度器、任务模型、合成服务，以及节点结果版本展示。

验收标准：

- [ ] 三镜头成片修改第二镜头，只提交一次新生成并重做合成，第一、第三镜头复用。
- [ ] 调整转场或片段顺序不重新生成镜头；仅移动节点不触发生成或合成。
- [ ] 下游确实引用改动节点产物时才标记失效，执行顺序依赖不造成无谓重做。
- [ ] 结果晚到、执行中再次修改、引用文件过期等情况都不会误用旧产物。

## 9. 第 7 阶段：结果检查与有限自动修正

目标：执行后能判断技术是否成功，并在明确标准下提出或执行有限修正。

改造任务：

1. 先实现可确定的技术检查：文件存在且可解码、时长与分辨率、约定音轨、所有必需镜头与合成输出是否完整。
2. 再按模型能力增加关键帧内容检查，将用户明确提出的主体、镜头和风格要求作为检查项；记录证据与不确定性。美感与角色一致性不能仅靠技术检查保证。
3. 把检查结果作为结构化数据反馈给规划器，输出可校验的修正计划；检查器不直接写图或提交生成。
4. 通过第 6 阶段重做最小影响范围，设置修正次数、额外费用和总时限，所有重新生成沿用同一预算规则。
5. 仅支持明确声明的结果分支，例如检查通过结束、可修复问题重试、无法判断转人工；达到限制或证据不足时给出结果和建议，不继续循环。

主要文件：新增结果检查服务、检查结果模型与路由，扩展编排状态机、局部运行服务和前端结果说明。

验收标准：

- [ ] 损坏文件、缺少必需片段和明显参数不符不会被标记为完成。
- [ ] 可修复问题生成局部修正计划，不无故重做全部视频。
- [ ] 达到预算、次数或时间限制后停止自动修正，保留已生成结果。
- [ ] 内容检查无法确定时明确交给用户判断，不把主观质量包装成确定结论。

## 10. 数据与交付约束

- 第 1 阶段尽量收敛入口改动；确需预算事务记录时单独增加兼容迁移。
- 第 2–4 阶段逐步增加导入映射、图修订、操作记录、运行节点关联和事件记录；新关联允许旧记录为空，不猜测旧任务属于哪个节点。
- 第 5–7 阶段补充执行尝试、控制状态、产物版本和检查结果；每次迁移都覆盖空库及现有库升级。
- 计划、画布和执行不要求使用同一张表，但必须能通过稳定 ID 和版本互相追溯；修改画布不修改正在运行的输入快照。
- 复用现有前端与后端技术栈。裁剪、字幕、配音、复杂时间线等新增视频能力需要另定功能范围；智能体工具不会凭空补出尚不存在的处理能力。

## 11. 测试与实施批次

每阶段仅增加能证明该阶段行为的回归，并运行受影响的现有检查。先用隔离数据库、模拟模型/供应商和短测试视频覆盖控制逻辑；真实服务联调按既定预算执行。

| 阶段 | 必须覆盖的测试 | 推荐独立交付批次 |
| --- | --- | --- |
| 1 | Ask/Auto/降级、重复接受、预算、画布归属与切换 | 入口与计划修复；共享接受服务及交互 |
| 2 | 素材转换、ID 映射、重复导入、图冲突、界面刷新 | 公共画布服务；转换与前端同步 |
| 3 | 长任务事件、双订阅、重连重放、旧结果隔离、恢复运行 | 运行关联及查询；事件持久化与前端接入 |
| 4 | 工具协议、参数拒绝、批次回滚、撤销冲突、人工接手 | 读取与编辑工具；操作历史及控制版本 |
| 5 | 依赖、并发上限、重试分类、取消、崩溃恢复与预算 | 调度及尝试记录；取消重试和恢复 |
| 6 | 精确失效范围、缓存复用、素材过期、只重做合成 | 版本与输入指纹；局部运行及回填 |
| 7 | 技术检查、有限修正、额外费用、无法判断分支 | 技术检查；内容检查与修正循环 |

首批实施只推进第 1 阶段，完成其验收后进入第 2 阶段。第 3 阶段完成时交付第一个可用闭环，再评估扩大接管范围。

最终演示：用户在已有画布上要求“做一个三镜头产品广告”，系统建立合法画布、执行并展示成片；随后要求“第二个镜头改成近景，其他不动”，系统只重做第二镜头及最终合成；期间用户能够查看进度、接手编辑、停止后续任务和恢复明确可重试的失败任务。
